# Agents

## Repository

- Turborepo + npm workspaces monorepo. Apps: `apps/copilot` (package `copilot`, the customer SaaS and identity/OAuth server, Next.js 16 App Router, React 19), `apps/projects` (package `projects`, at `projects.copilot.asynchrone.space`), `apps/calendars` (package `calendars`, calendars and meetings at `calendars.copilot.asynchrone.space`), `apps/files` (package `files`, files and their upload/download APIs at `files.copilot.asynchrone.space`), `apps/messages` (package `messages`, the messaging domain app at `messages.copilot.asynchrone.space`), `apps/clients` (package `clients`, the CRM at `clients.copilot.asynchrone.space`), `apps/employees` (package `employees`, the HR app at `employees.copilot.asynchrone.space`), `apps/control-tower` (package `control-tower`, internal platform administration) and `apps/landing` (package `landing`, the stateless public marketing site at `asynchrone.space`). Shared packages: `packages/db` (`@workspace/db`), `packages/ui` (`@workspace/ui`), `packages/i18n` (`@workspace/i18n`), `packages/next-config` (`@workspace/next-config`), `packages/eslint-config`, `packages/typescript-config`. The cross-app Playwright suite is the `packages/e2e` workspace (`@workspace/e2e`), not a deployable app.
- Run tasks from the repo root through Turbo: `npm run dev|build|lint|typecheck|format`. Target one workspace with `--workspace=copilot`, `--workspace=projects`, `--workspace=calendars`, `--workspace=files`, `--workspace=messages`, `--workspace=clients`, `--workspace=employees`, `--workspace=control-tower` or `--workspace=landing` (or `-w`).
- `main` is protected: land changes via PR. The `ci` job (`.github/workflows/turbo.yml`) runs typecheck → lint → build; `.github/workflows/helm.yml` lints the umbrella and renders every app alias.

## Verify before finishing

- `npm run test:unit` runs every workspace unit suite through Turbo. There is no single root `test` script for e2e; use the targeted commands below.
- Run, in order: `npm run lint && npm run typecheck && npm run build` (matches CI), `npm run test:unit` (every workspace), then the targeted e2e suites below (vitest files are `*.unit.test.ts` next to the code). `npm run test:e2e --workspace=copilot` runs Playwright against a migrated database (CI does this in the `e2e` job); `e2e/portal.spec.ts` seeds its own client company and drives the real invitation flow, so it needs no extra fixture data. `npm run test:e2e --workspace=projects` provisions its OAuth client (`apps/projects/e2e/bootstrap.ts`), starts Copilot and the projects app and covers sign-in, organization switching and a project/task flow (CI runs it in `e2e-projects`). `npm run test:e2e --workspace=calendars` and `--workspace=files` follow the same shape (`e2e-calendars` / `e2e-files`) and cover sign-in, organization switching, creating a calendar event, the meeting settings screen and a real upload/download through the files API. `npm run test:e2e --workspace=messages` provisions `asynchrone-messages` the same way and covers sign-in, organization switching, a conversation with an attachment upload/download round trip, cross-organization rejection and the old Copilot URL redirect (CI runs it in `e2e-messages`). The same shape covers `clients` and `employees` (`e2e-clients`, `e2e-employees`), including the authorization failures: a member sees no payroll/admin data and an id from another organization is unreachable.
- Cross-domain contracts (needs a migrated PostgreSQL; no browser): `npm run test:contracts`. The suite lives in `apps/copilot/scripts/contracts` and pins package exports, the member directory, notifications, recents, search, export/deletion and the MCP/assistant tool surface; it also replays the issue #40 cross-org/impersonation attacks. CI runs it in the `contracts` job. See `docs/contract-tests.md`.
- Cross-app browser suite (needs a migrated PostgreSQL): `npm run test:e2e --workspace=@workspace/e2e` (`packages/e2e`). It spawns the apps' own e2e bootstraps, starts Copilot (3020), projects (3021) and calendars (127.0.0.1:3022) and covers one Copilot session with two relying parties: sign-in, access-token refresh, organization-switch revocation, back-channel logout, the control-tower impersonation handoff (banner, single use, one-hour TTL, stop), audience binding, stale sessions and failure injection (`apps/copilot/scripts/e2e-cross-app-probe.ts`). CI runs it in `e2e-cross-app`. See `docs/cross-app-e2e.md`.
- Workspace boundaries: `npm run check:boundaries` fails on a package→app import, an app→app import, an undeclared `@workspace/*` dependency, a relative import that escapes its workspace, or a cross-`@workspace/db-*` import. CI runs it after lint.
- Fleet Helm checks (needs Helm on PATH): `npm run verify:helm` builds the vendored generic chart, lints the umbrella, renders every app alias on its own and renders the generic chart standalone; it asserts both wildcard certificates, the apex/www ingress rules, the Copilot discovery URLs, the single-owner CronJob set, the per-app scrape annotations, the fleet alert names and that an over-budget pool or fleet fails the release. `.github/workflows/helm.yml` runs it.
- Connection budget check (no DB needed): `npm run verify:connection-budget` cross-checks `packages/db-core/src/budget.ts`, the per-app `DATABASE_POOL_MAX`/replica values in `charts/asynchrone-space/values.yaml` and the documented topology, and fails when the fleet would exceed the budget (ADR 0038).
- Per-app migrations: `npm run db:create && npm run migrate:deploy && npm run verify:migrations` (needs a live PostgreSQL). The migrate image runs the monolith migration first, then the ordered per-app orchestrator.
- Database split (maintenance window; needs source and target databases): `npm run split:databases -- --dry-run`, then `--all`. Large-object OIDs are preserved. See `docs/database-split.md`.
- The Turbo `generate` task (`prisma generate` → `packages/db/lib/generated/prisma`) is a dependency of `build`/`typecheck`/`dev`. After editing a schema, run `npm run split:prisma` for generated per-app schemas and `npm run generate:all` (or the matching `@workspace/db-*` workspace) for the clients.
- Manual Team trial check (needs a live DB; identity only: start, abuse checks, D-3 reminder, idempotent expiry): `npm run verify:trial --workspace=copilot`.
- Cross-organization authorization is covered by each domain app's `e2e/authorization.spec.ts` and by the cross-app suite; the retired in-process `verify:authorization` script was removed with the monolith binding (#171).
- Legal copy parity (no DB needed): `npm run verify:legal-copy --workspace=landing`. It fails when the `en` and `fr` legal documents disagree on a key, or when a table or list in `legal.json` is malformed.
- Landing stateless invariant (no DB needed): `npm run verify:stateless --workspace=landing`. It fails when `apps/landing` imports `@workspace/auth`, `@workspace/db*`, `@workspace/oidc`, `@workspace/service-auth`, `@workspace/sagas`, `@workspace/app-shell`, Prisma, `better-auth` or `pg`, accesses a cookie, or declares such a dependency.
- Landing unit tests (no DB needed): `npm run test:unit --workspace=landing`. They pin the legacy apex → Copilot redirect map and the stateless import graph.
- Legal PDFs: `npm run legal:pdfs --workspace=landing` regenerates `apps/landing/public/downloads/legal` from the same copy (needs Chromium; `npx playwright install chromium` once). Commit the PDFs with the copy that produced them — see `docs/legal/README.md`.
- Control-tower auth invariant (no DB needed): `npm run verify:auth-config --workspace=control-tower`. It fails if cross-subdomain cookies are enabled, sign-up is opened, the Copilot auth secret is reused, or the 2FA plugin is missing. It also runs the fleet check: no app may set a `Domain=`/cookie-domain option or a `.copilot` cookie, every domain app must keep the OIDC routes, signed back-channel logout, session switch cleanup and an audience-bound internal service verifier, and Copilot must fan out organization-switch revocation.
- Manual platform-authorization check (needs a live DB): `npm run verify:platform-authorization --workspace=control-tower`. It covers role resolution, the IP allowlist, single-use handoff claims, the cutover invariant (only platform accounts in the platform database) and a real Better Auth sign-in against it.
- Control-tower database cutover (needs a live DB; dry run by default): `npm run cutover:control-tower --workspace=control-tower -- --dry-run`, then `--apply`, `--verify`. It copies only platform operators (plus accounts, sessions, TOTP, `platformAuditEvent`, `platformHandoff`) into `asynchrone_control_tower`; `--user <email> --apply` provisions one operator. See `docs/control-tower-database.md` for the maintenance window and rollback.

## Environment & data

- Env lives in `apps/copilot/.env` (Next loads it from the app cwd; `packages/db/prisma.config.ts` loads it explicitly, falling back to a package-local `.env`). Start from `apps/copilot/.env.example`. `CONTROL_TOWER_URL` (the control tower origin) is used by the "Stop impersonating" flow.
- The projects app has its own `apps/projects/.env` (Next loads it from that app's cwd; `apps/projects/.env.example`): `PROJECTS_APP_URL`, `COPILOT_APP_URL`, the provisioned `PROJECTS_OAUTH_CLIENT_ID/SECRET`, `DATABASE_URL` and `CRON_SECRET` (it owns the hourly `repository-sync` CronJob since #168). `PROJECTS_APP_URL` must match the client's registered redirect/logout URIs, so it is `http://localhost:3004/api/auth/callback` locally.
- The calendars app (`apps/calendars/.env`, port 3005) and the files app (`apps/files/.env`, port 3006) follow the same shape with `CALENDARS_APP_URL` / `FILES_APP_URL`, the provisioned `CALENDARS_OAUTH_CLIENT_ID/SECRET` and `FILES_OAUTH_CLIENT_ID/SECRET`, and `DATABASE_URL`. The files app also reads `CRON_SECRET` for its `uploads-sweep` route.
- The messages app has its own `apps/messages/.env` (same shape; `apps/messages/.env.example`): `MESSAGES_APP_URL` (`http://localhost:3007` locally), `COPILOT_APP_URL`, `MESSAGES_OAUTH_CLIENT_ID/SECRET`, `DATABASE_URL` and `MESSAGES_DATABASE_URL`.
- The clients app has its own `apps/clients/.env` (`apps/clients/.env.example`): `CLIENTS_APP_URL` (default `http://localhost:3008`), `COPILOT_APP_URL`, the provisioned `CLIENTS_OAUTH_CLIENT_ID/SECRET` and `DATABASE_URL`. The employees app mirrors it on `http://localhost:3009` with `EMPLOYEES_*`.
- The control tower has its own `apps/control-tower/.env` (`apps/control-tower/.env.example`): `CONTROL_TOWER_DATABASE_URL` (its own database, never `DATABASE_URL`), `BETTER_AUTH_URL` (its own origin), `CONTROL_TOWER_BETTER_AUTH_SECRET` (≥32 chars, different from `BETTER_AUTH_SECRET`), `PLATFORM_APP_URL` (Copilot's origin). `DATABASE_URL` in that file is only the cutover script's source.
- `docker compose` loads `apps/copilot/.env` into the `copilot` container (its `environment` block still overrides `DATABASE_URL`/`BETTER_AUTH_URL`), so local dev and Docker share `BETTER_AUTH_SECRET`; rotating that secret breaks the encrypted JWKS rows in the DB — clear the `jwks` table to regenerate them.
- One `Dockerfile` builds any app with `--build-arg APP=copilot|projects|calendars|files|messages|clients|employees|control-tower|landing`; `docker compose` serves the landing on 3002, Copilot on 3003, projects on 3004, calendars on 3005, files on 3006, messages on 3007, clients on 3008, employees on 3009 and the control tower on 3001. `.dockerignore` excludes `.env` files at any depth — never bake local secrets into an image.
- `generate` and the `copilot`/`control-tower` builds require `DATABASE_URL`, `BETTER_AUTH_SECRET`, and `BETTER_AUTH_URL` to be set; CI and Docker use non-connecting placeholders. The landing is stateless and builds with none of them (CI has a dedicated `landing` job that proves it).
- When adding an env var, also add it to the `env` arrays in `turbo.json` (build + dev) so Turbo passes it through, update `.env.example`, and add a build-time placeholder in `Dockerfile` / `.github/workflows/turbo.yml` if it is read at build time.
- `DATABASE_POOL_MAX` is per app and clamped by `@workspace/db-core` to the app ceiling in `packages/db-core/src/budget.ts` (ADR 0038): Copilot 8, files 6, projects/calendars/messages/clients/employees 4, control tower 3, migrate 5. Each app's `@workspace/db-<domain>` package owns one `pg.Pool` shared by Prisma and the large-object code; `apps/<app>/lib/prisma.ts` re-exports it. The Helm chart enforces the same budget, and `npm run verify:connection-budget` fails on drift. Math and PgBouncer/role-limit guidance: `docs/deployment/database-operations.md`.

## Deployment

- `.github/workflows/docker.yml` publishes ten GHCR images: `asynchrone-space-copilot` (Copilot runner), `asynchrone-space-projects`, `asynchrone-space-calendars`, `asynchrone-space-files`, `asynchrone-space-messages`, `asynchrone-space-clients`, `asynchrone-space-employees` (domain runners), `asynchrone-space-control-tower` (control-tower runner), `asynchrone-space-landing` (landing runner) and `asynchrone-space-migrate` (Dockerfile `migrate` stage).
- Helm charts live in `charts/`: `asynchrone-space-app` is the one generic app chart (Deployment, Service, Ingress, ConfigMap, Secret ref, PDB, HPA, NetworkPolicy, CronJobs, helm test); `asynchrone-space` is the umbrella (nine dependency aliases, migration hook, wildcard Certificates and production values). Each alias (`landing`, `copilot`, `projects`, `calendars`, `files`, `messages`, `clients`, `employees`, `control-tower`) sets `nameOverride`, image, host and config, so resources stay `asynchrone-space-<app>-*`. The landing ingress owns `asynchrone.space` and redirects `www` to the apex; Copilot serves `copilot.asynchrone.space`; domain apps serve `*.copilot.asynchrone.space`; the control tower serves `control-tower.asynchrone.space`. Two cert-manager certificates (`asynchrone-space-tls` for the apex + `*.asynchrone.space`, `asynchrone-space-domain-tls` for `*.copilot.asynchrone.space`) are rendered unless `certificates.enabled=false`. Install/upgrade from the root with `helm dependency build charts/asynchrone-space` then `helm upgrade --install asynchrone-space charts/asynchrone-space -n asynchrone-space --set global.imageTag=sha-…`. The packaged generic chart under `charts/asynchrone-space/charts/` is committed (Git-based chart sources such as Rancher never run `helm dependency build`); after editing it, run `helm dependency build` and commit the archive — CI verifies it matches the source.
- The charts require the existing Secrets `asynchrone-space-copilot-secrets` (DATABASE_URL, IDENTITY_DATABASE_URL and the per-app `*_DATABASE_URL` keys for the migrate Job, BETTER_AUTH_SECRET, CRON_SECRET, optional provider keys), `asynchrone-space-projects-secrets` (DATABASE_URL, PROJECTS_OAUTH_CLIENT_ID, PROJECTS_OAUTH_CLIENT_SECRET, CRON_SECRET), `asynchrone-space-calendars-secrets` (DATABASE_URL, CALENDARS_OAUTH_CLIENT_ID, CALENDARS_OAUTH_CLIENT_SECRET), `asynchrone-space-files-secrets` (DATABASE_URL, CRON_SECRET, FILES_OAUTH_CLIENT_ID, FILES_OAUTH_CLIENT_SECRET), `asynchrone-space-messages-secrets` (DATABASE_URL, MESSAGES_OAUTH_CLIENT_ID, MESSAGES_OAUTH_CLIENT_SECRET), `asynchrone-space-clients-secrets`, `asynchrone-space-employees-secrets` (same shape) and `asynchrone-space-control-tower-secrets` (CONTROL_TOWER_DATABASE_URL, CONTROL_TOWER_BETTER_AUTH_SECRET). The landing mounts no Secret. Never put secrets in values or templates.
- The pre-install/pre-upgrade `asynchrone-space-migrate` Job runs `prisma migrate deploy`; Copilot owns the four identity CronJobs (`trial-expiry`, `organization-deletion`, `audit-retention`, `data-exports`), projects owns `repository-sync` (hourly since #168) and files owns `uploads-sweep` (daily 03:00). Every cron has exactly one owner; the repository webhook route lives in projects. See `docs/deployment/helm.md` and ADR 0019.
- Verify chart changes with `npm run verify:helm` (or `helm dependency build charts/asynchrone-space && helm lint --strict charts/asynchrone-space --set global.imageTag=test && helm template asynchrone-space charts/asynchrone-space --set global.imageTag=test`). `docker compose config` must also pass; compose starts every app on ports 3001–3009.

## Prisma / database

- Prisma 7 with the `@prisma/adapter-pg` driver adapter (not the default connector).
- Schema and migrations live in `packages/db/prisma`; apply with `cd packages/db && npx prisma migrate deploy`. Create migrations from `packages/db`.
- `@workspace/db` validates only database env (`DATABASE_URL`, `DATABASE_POOL_MAX`). App-specific requirements stay in each app's own `lib/env.ts`. `createPool` also sets `application_name`, a 30s `idle_in_transaction_session_timeout` and a 5-minute `statement_timeout`.
- File bytes are stored as PostgreSQL large objects in the same DB as metadata — no external object store (Vercel Blob was removed). See `apps/copilot/lib/large-object.ts`.

## Audit log

- `AuditLog` is the customer-facing trail (Settings → Audit log) and exists in every per-app schema. Shared logic lives in `@workspace/audit` (`packages/audit`), parameterized by the app's database client. Write it only through `apps/copilot/lib/audit/record.ts` (`recordUserAudit` for server actions, `recordSystemAudit` for jobs/webhooks), never with `prisma.auditLog.create` — that is what keeps the page, the export and the retention job consistent.
- Every app exposes `/internal/v1/audit`, `/audit/facets`, `/audit/export` and `/audit/prune` through `packages/audit/src/http.ts`, gated by `internal:audit:read` / `internal:audit:write`. Copilot merges them with `apps/copilot/lib/audit/fanout.ts` (composite cursor, partial results); configure `*_APP_URL` to enable a domain app.
- The mutation that performs a change records the row itself (one row per changed entity), snapshots `entityLabel`, and lets a failed audit write fail the action.
- New actions go into `AUDIT_ACTIONS` and get `Audit.actions.<action>` labels in `packages/i18n/messages/{en,fr}/audit.json`; unknown actions fall back to their raw value.
- Member, role and invitation changes go through Better Auth, so they are audited from the `after` hook in `apps/copilot/lib/auth.ts` (`apps/copilot/lib/audit/auth-audit.ts`).
- Reads and exports are gated by `roleRank >= admin` and the `auditLog` entitlement (Enterprise). Retention is 30 / 365 / 730 days (Free / Team / Enterprise, overridable on Enterprise) and is pruned by the `audit-retention` CronJob, which must never touch `PlatformAuditEvent`. See `docs/audit-log.md` and ADR 0027.

## Control tower

- Internal app at `apps/control-tower` (port 3001). Platform roles live in the comma-separated `user.role`: `platform_admin` (full) and `platform_support` (read-only for now). Grant one with `npm run grant:platform-role --workspace=control-tower -- --email you@example.com`; the account must then enroll a TOTP device at `/setup-2fa`.
- It owns `asynchrone_control_tower` (`@workspace/db-control-tower`) for platform users, sessions, accounts, TOTP, `PlatformAuditEvent` and its `PlatformHandoff` copy. It never imports `@workspace/db` (enforced by `check:boundaries`); every customer read model comes from `/internal/v1/admin/*` through `IdentityAdminClient`. See `docs/control-tower-database.md` and ADR 0034.
- Operators are provisioned by signing up in Copilot, then `npm run cutover:control-tower --workspace=control-tower -- --user you@example.com --apply` and a role grant. The full cutover/rollback runbook is `docs/control-tower-database.md`.
- Every platform role requires TOTP (`twoFactor` plugin; `TwoFactor` table and `user.twoFactorEnabled`). `requirePlatformContext()` redirects unenrolled operators to `/setup-2fa` and rejects server actions; `requirePlatformSession()` is the 2FA-free variant used only by that page.
- Optional `PLATFORM_ALLOWED_IPS` (comma-separated IPv4/CIDR or `*`) restricts the control tower to known networks as defense in depth. Unset allows every address; in-app auth still applies.
- Its Better Auth instance is deliberately separate: own secret, own host-only cookie (`asynchrone-space-control-tower.session_token`), sign-up disabled, no `jwt`/`mcp`/`organization` plugins. **Never enable `advanced.crossSubDomainCookies`** — see ADR 0018 and `verify:auth-config`.
- Pages guard with `requirePlatformContext()`; anonymous users go to `/sign-in`, signed-in users without a platform role get `notFound()`. Server actions use `requirePlatformContext({ surface: "action" })` / `withPlatformAction`.
- Platform mutations write `PlatformAuditEvent` rows (never the org-scoped `AuditLog`). Impersonation uses the single-use `PlatformHandoff` table, not a shared cookie.
- Platform mutations are server actions under `apps/control-tower/actions/`. Each uses `withPlatformAction`, enforces `platform_admin` for destructive changes (`platform_support` may revoke sessions), appends a `PlatformAuditEvent`, and revalidates the affected path. Customer identity changes go through Copilot's `/internal/v1/admin/*` with `IdentityAdminClient` (`internal:identity:admin`), never a direct identity-database write.
- Impersonation is a single-use handoff, never a shared cookie: the control tower stores a hashed token in `PlatformHandoff` and redirects to `${PLATFORM_APP_URL}/api/platform/handoff?token=…`; the Copilot route claims it, creates a 1-hour session with `impersonatedBy`, and signs its own cookie. `apps/copilot/app/[locale]/(app)/layout.tsx` shows the banner and deletes the session once it is an hour old; `/api/platform/stop-impersonating` deletes it and returns to `CONTROL_TOWER_URL`.
- `apps/copilot/lib/auth.ts` registers the same `admin()` plugin (roles map + `adminRoles: ["platform_admin"]`) so bans apply to customer sign-in.

## Code layout & conventions

- Path aliases: `@/*` → the app's own directory, `@workspace/ui/*` → `packages/ui/src/*`. UI imports require `transpilePackages` (already set in `next.config.ts`).
- Domain apps follow one template, documented in `docs/domain-app-template.md` (ADR 0036): `/{locale}/{orgSlug}/<domain>` on their own host, the shared shell, a host-only `@workspace/oidc` session in their own `oidcSession` table (`PrismaOidcSessionStore`), the `requireWorkspace()` gates (live Copilot session, token/route organization, 2FA policy), the `/api/auth/switch` handoff to Copilot's `select-organization` page, a `lib/env.ts` registry, an `APP=<domain>` image, an instance of the generic Helm app chart and Playwright coverage. `apps/projects` is the reference (pages, actions, session, shell and deployment moved there in #160); `apps/calendars` and `apps/files` followed in #161, `apps/messages` in #162, and `apps/clients`/`apps/employees` in #163. Copilot 308-redirects the old `/{locale}/{orgSlug}/projects|calendars|files|messages|clients|contacts|deals|employees|hr` paths in `apps/copilot/proxy.ts` and no longer mounts a project, calendar, files, messaging, client or employee provider.
- Every domain app binds exactly one `@workspace/db-<domain>` package (#171). Identity rows (`member`, `user`, `account`), the member directory and portal access go through Copilot's `/internal/v1/*` APIs; projects/clients capacity and links go through the projects internal API. The repository webhook (`/api/webhooks/repositories/:id`) and the hourly `repository-sync` cron both live in `apps/projects`. Never import two database packages in one app.
- `@workspace/contracts` owns the app/database registry and the versioned `/internal/v1` schemas. Import from the package root for shared metadata; `@workspace/contracts/server` is server-only because it reads runtime app origins. Internal APIs must use these contracts rather than inventing their own shapes. See `docs/architecture/domain-apps.md`.
- Per-app databases live in `@workspace/db-<domain>` packages, with `@workspace/db-core` for the shared pool and the fleet connection budget. Every `createPool` call passes its `app` key. Their Prisma schemas are generated by `npm run split:prisma`; do not hand-edit them. `npm run verify:prisma-schemas` validates all schemas. See `docs/databases.md`.
- Plan and trial rules are dependency-free in `@workspace/core/plans` and `@workspace/core/trial` (`entitlementsFor`, `parsePlan`, `effectivePlan`, `monthWindow`, …), so every app can resolve the same plans without importing a database package.
- UI is shadcn/ui on **Base UI** primitives (not Radix) with Tailwind. Owned components live in `packages/ui/src/components`.
- `pg` and `pg-large-object` are listed in `serverExternalPackages`; keep them out of client code.
- Rate limits are shared across replicas through the `rateLimit` table (ADR 0022): use `rateLimit`/`assertRateLimit` from `packages/core/src/rate-limit.ts` and choose `failOpen` per call site. Better Auth limits auth endpoints through the same table.
- Tests live next to their code: `*.unit.test.ts` (vitest) beside a module, `apps/<app>/e2e/*.spec.ts` for one app against Copilot, and `packages/e2e/e2e/*.spec.ts` for the cross-app flows. The cross-app suite must not import an app: it spawns `apps/copilot/scripts/e2e-cross-app-probe.ts` when it needs a Copilot-side fan-out and provisions OAuth clients by spawning each app's `e2e/bootstrap.ts`.
- Sign-up abuse controls (`packages/auth/src/signup-policy.ts`, wired through `@workspace/auth` and `apps/copilot/lib/auth.ts`): Cloudflare Turnstile on `/sign-up/email` and `/request-password-reset` when `TURNSTILE_SECRET_KEY` is set (`TURNSTILE_SITE_KEY` must be set too, or the app refuses to boot), a disposable-domain blocklist plus `SIGNUP_BLOCKED_EMAIL_DOMAINS`, and optional `SIGNUP_INVITE_ONLY`. The `user.create.before` hook applies them to OAuth sign-ups too; keep it that way when adding a provider.
- Billing lives in `apps/copilot/lib/billing` (repository/provider/notifier ports, `service.ts` for the state machine, `plans.ts` for status → plan). Plan enforcement reads `subscription.plan` first and falls back to `organization.metadata.plan` through `resolvePlan()` in `packages/organization/src/entitlements.ts` (bound in `apps/copilot/lib/organization/entitlements.ts`) — every entitlement goes through it. Stripe webhooks arrive at `apps/copilot/app/api/webhooks/stripe/route.ts` (signature-verified, idempotent through `BillingEvent`; a failed delivery is re-claimed on Stripe's retry). Manual/Enterprise grants set `manualOverride` and are made from the control tower. See `docs/billing.md` and ADR 0023.
- The workspace shell (resolver, banners, nav, recents and appearance) lives in `@workspace/app-shell`; apps pass their app-local session and domain slots. Domain screens load their own data.
- Support (#101, ADR 0039): the ticket form at `/{orgSlug}/feedback` writes a `supportTicket` row (identity DB) and emails `FEEDBACK_EMAIL_TO`; the control tower works the queue at `/support` through `/internal/v1/admin/support-tickets` and audits each transition. `WorkspaceShell` takes `copilotUrl` and renders the shared help menu/footer (`@workspace/app-shell/support`); `GET /api/status` on Copilot redirects to `STATUS_PAGE_URL`. Channels, severities and response targets live only in `@workspace/core/support` (rendered by the landing `/support` page). Runbook: `docs/operations/support.md`.
- Observability lives in `@workspace/observability` (`/next` for Next-aware helpers): structured request logs, the Prometheus registry and the correlation-id helpers. Every app (including the landing and the control tower) has `instrumentation.ts` + `instrumentation-client.ts` (Sentry, disabled while `SENTRY_DSN` is empty), `GET /api/health` (own dependency check + pool snapshot) and `GET /api/metrics`. New route handlers use `withObservedRoute`/`createCronRoute`; `createDomainHandler` times itself. See `docs/observability.md`.
- Correlation ids: each app's proxy adopts `x-request-id`/`?rid=` or mints one, echoes it and stores it in a host-only non-HttpOnly `asynchrone_rid` cookie; the app shell appends `rid=` to cross-app links and the delegated domain client forwards `x-request-id`. It is a log field only — never authorize on it.
- Cross-app cache invalidation is explicit: each customer app serves `POST /internal/v1/invalidate` (`internal:cache:write`, `createInvalidationHandler`) and Copilot's `revalidateOrgPath` fans out after an organization-scoped mutation in `after()`, best-effort and logged. Today cross-app reads are `no-store`; register a tag when adding a `use cache` read. See ADR 0038.
- Cross-domain services are port-parameterized packages: `@workspace/storage` (large objects for the files app), `@workspace/notifications`, `@workspace/integrations` (provider clients; tokens stay in the owning app), `@workspace/ai` (agent, pricing and quota ledger), `@workspace/appearance` (organization preferences), `@workspace/billing` (plans and subscription state machine) and `@workspace/audit`. The owning app binds its database client, pool, provider or notifier in `apps/copilot/lib/*`; packages never open another app's database.
- Calendars and meetings live in `@workspace/calendars` (calendars, members, events, attendees, date helpers) and `@workspace/meetings` (settings, client requests, slots, provider adapters). Both are Next-free and take structural `CalendarDb`/`MeetingDb` ports and a `MeetingNotifier`; `apps/calendars/lib/{calendars,meetings}/index.ts` bind the database client and the notification inbox, and `apps/copilot/lib/{calendars,meetings}/index.ts` keep Copilot's own instances for the search adapter; the assistant, MCP and portal use the calendars delegated internal API (#190).
- Calendars/meetings screens and actions live in `apps/calendars` (`components/{calendars,meetings}`, `lib/{calendars,meetings,workspace-nav,permissions}`, `actions/{calendars,meetings,project-tasks}`); meeting settings moved with them (`/{locale}/{orgSlug}/calendars/settings`) and Copilot's organization settings tab links there, while the portal keeps the client-side request/cancel actions in `apps/copilot/actions/meetings.ts`. The project task overlay reads tasks through the projects internal API (`list-calendar-tasks`). The files screens, actions, upload/download APIs and the `uploads-sweep` route live in `apps/files`; the portal keeps its own document upload/download on Copilot. Search, export and deletion run in `apps/files`; the assistant, MCP and portal call the files delegated internal API (#190).
- Projects/tasks/templates/labels/comments and the GitHub/GitLab repository sync live in `@workspace/projects` (repository, service, schemas, types, UI). Since #160 the screens and their server actions live in `apps/projects` (`actions/*`, `lib/{projects,integrations}`, `lib/project-actions.ts`); the webhook route lives there too. The assistant, MCP and portal call the projects delegated internal API; Copilot has no project adapter. The package takes the actions as a port (`ProjectActions`) and never imports `@/actions/*`.
- Organization roles, permissions, entitlements, shell queries, paths and the member-directory contract live in `@workspace/organization`; `apps/copilot/lib/organization/*` files are app adapters.
- The files domain lives in `@workspace/files`: the file tree, versions, shares, chunked upload sessions (ADR 0010), the screens and the large-object unlink path used by data export and organization deletion. `apps/files/lib/{files,large-object,rate-limit,entitlements}.ts` bind the database, audit writer, plan checks, quota reader, rate limiter and large-object store; `apps/files/components/files-provider.tsx` binds the actions, member directory and navigation state.
- Clients/contacts/deals/pipelines/fields/activities/documents live in `@workspace/clients`; employee profiles/attendance/leave/balances/settings/salary/capacity live in `@workspace/employees`. Both own access checks, schemas, services, CSV/date helpers, types and UI. Since #163 the screens, server actions and adapters live in `apps/clients` (`actions/clients.ts`, `lib/clients`, `lib/client-actions.ts`) and `apps/employees` (`actions/employees.ts`, `lib/employees`, `lib/employee-actions.ts`); the org layout injects them as `ClientActions`/`EmployeeActions`, so no package component imports `@/actions/*`. Copilot reaches clients/employees only through the delegated internal API; the assistant, MCP and portal use the same. Salary and payroll stay behind `isAdmin`/`requireAdmin`. Portal access management still needs Copilot's Better Auth invitations, so the client detail card is read-only on the clients host (the list itself comes from the identity API).
- The messaging domain lives in `@workspace/messaging`: conversations, members, messages, reactions, threads, attachments, unread state and the chat screens. Since #162 the screens, actions, attachment endpoints and upload sessions live in `apps/messages`; `apps/messages/lib/messaging.ts` binds `@workspace/db-messages` and its own large-object store, and `apps/messages/components/messaging-provider.tsx` binds the server actions (mutations), the polling reads (`/api/messages/snapshot`, `/api/messages/conversations/[id]`, `/api/messages/presence` — route handlers, never server actions, so a poll cannot abort a navigation) and the member directory. Attachments are transient upload sessions backed by large objects in the messages database; Copilot reaches messages only through `/internal/v1/domain/:operation`.
- The client portal domain lives in `@workspace/portal`: portal context and client-member authorization, dashboard/project/task/document read models, document upload and download, the shared project thread and task comments, portal access management and the client meetings read model. `apps/copilot/lib/portal/index.ts` binds the identity Prisma client, `@workspace/storage`, Better Auth invitations and notifications, and reaches projects, clients, files and meetings through delegated internal clients (`DomainClient`, #190); `apps/copilot/lib/portal/context.ts` resolves `Member.clientId` from the session, and `apps/copilot/app/[locale]/portal/layout.tsx` passes the server actions through `PortalActions`. Portal routes and APIs stay in Copilot (there is no `apps/portal`), and portal accounts (`role=client`) must never reach the internal workspace. A client account exists only after it accepts a portal invitation (`PortalInvite` + `Member.clientId`): `apps/copilot/app/[locale]/(app)/layout.tsx` and `[orgSlug]/layout.tsx` redirect it to `/portal`, `getRequestContext` rejects it on internal APIs, `getTwoFactorPolicy` leaves it out of the 2FA requirement, and the portal layout sends internal members back to their workspace. `e2e/portal.spec.ts` pins both directions.
- The Better Auth server configuration and shared session helpers live in `@workspace/auth`; `apps/copilot/lib/auth.ts` only injects the identity database, mailers, audit writers, plan checks and OAuth server resources.
- Customer 2FA uses the same `twoFactor` plugin mapped to its own `customerTwoFactor` table and `user.customerTwoFactorEnabled` column; never point it at the control tower's `twoFactor` table (different encryption secret). See `docs/two-factor.md`.
- Copilot is the OAuth 2.1/OIDC authorization server through `mcp()`; never register `oauthProvider()` alongside it. App resources, scopes, token lifetimes and claims live in `apps/copilot/lib/oauth`; see `docs/oauth-server.md`.
- Workspace apps consume `@workspace/oidc` for the authorization-code flow, host-only session cookie, token refresh, JWKS verification and back-channel logout. Never implement a second OAuth client. `resolveSession` re-verifies issuer, audience, signature and expiry (60-second skew) on every request and deletes the row when the token's `sub`/`sid`/organization or a refreshed token no longer matches. Organization switch deletes the local session and Copilot fans out `POST /internal/v1/auth/revoke`; stop-impersonation deletes the Copilot session through Better Auth so back-channel logout fires. See `docs/oidc-client.md`.
- First-party OAuth clients are declared in `apps/copilot/lib/oauth/clients.ts` and provisioned/rotated with `npm run oauth:clients --workspace=copilot`. Never create them by hand. See `docs/oauth-clients.md`.
- Internal service calls use `@workspace/service-auth`: OAuth client credentials, audience-bound tokens, a per-audience cache and a verifier for `/internal/v1/*`. Never use a shared secret or an unauthenticated call. The assistant, MCP and portal use the delegated domain call (`POST /internal/v1/domain/:operation`, `DomainCallSchema`, `internal:domain:read/write`) and pass the user, organization, role, impersonation and portal context; the target app enforces its own rules and writes its audit row. Mutations accept `Idempotency-Key`. The verifier expects `iss = ${COPILOT_APP_URL}/api/auth` and the target app's own `internalAudience` (the bare origin is accepted for older tokens); domain apps also expose `POST /internal/v1/auth/revoke` for the organization-switch fan-out. See `docs/internal-service-auth.md`.
- Cross-database export/deletion are durable sagas in `@workspace/sagas`: identity state in `organizationDeletionJob` / `userDeletionJob` / `dataExportApp`, per-app idempotent endpoints, retries that resume at the failed app, identity deleted last, and an export marked ready only when every part is complete. See `docs/domain-app-sagas.md`.
- Notifications are created in Copilot with `(organizationId, idempotencyKey)`; search is a per-app `/internal/v1/search` fanned out with timeouts and partial results. Recents stay per app. See `docs/search-and-notifications.md`.
- The identity internal API is `apps/copilot/app/internal/v1/**` (identity DB, `internal:identity:read`) and its typed client is `IdentityClient` in `@workspace/contracts`. Use `invalidate(organizationId)` after member/role mutations. See `docs/identity-api.md`.
- Organization deletion is a two-step flow: an owner schedules it (`lib/organization/deletion-service.ts`, `organization.deletionScheduledAt`), every member sees a banner, and the daily `organization-deletion` cron deletes overdue organizations, their large objects and the FK-less rows (`uploadSession`, `platformHandoff`). Better Auth's own `organization.delete` is disabled so nothing bypasses the grace period.
- i18n uses next-intl with `localePrefix: "always"` (en default, fr). Add every user-facing string to both `packages/i18n/messages/en` and `packages/i18n/messages/fr`; blog/content MDX is mirrored under `apps/landing/content/<type>/<locale>`.
- Legal documents are data, not JSX: sections live in `apps/landing/lib/landing/legal.ts`, copy in `packages/i18n/messages/{en,fr}/legal.json`, printable versions in `apps/landing/public/downloads/legal`. See `docs/legal/README.md` before adding a document or a sub-processor.
- The landing must never import `@workspace/auth`, `@workspace/db`, `@workspace/oidc` or Prisma: it has no session and no database. Header account actions link to `copilot.asynchrone.space`, configured at build time with `NEXT_PUBLIC_WORKSPACE_URL` (`apps/landing/.env.example`); canonical URLs, `robots.txt` and `sitemap.xml` use `NEXT_PUBLIC_SITE_URL`. `createNextConfig({ workspacePackages })` keeps its transpile list to `@workspace/ui` and `@workspace/i18n`.
- `apps/landing/proxy.ts` redirects legacy apex workspace paths to Copilot with a 308: the auth flows (`sign-in`, `sign-up`, `forgot-password`, `reset-password`, `two-factor`, `verify-email`, `consent`), onboarding, `select-organization`, `accept-invitation`, `portal`, `settings`, `search`, `help`, `feedback`, `mcp`, `api/assistant` and organization-scoped sections (`/<orgSlug>/{settings,search,help,feedback,projects,files,messages,calendars,employees,clients,hr}`); Copilot then 308-redirects `projects` and `clients|contacts|deals|employees|hr` to their own hosts. Copilot serves `/search`, `/help` and `/settings` (which redirects to `/settings/account`) as workspace-wide fallbacks. `MARKETING_SEGMENTS` protects the marketing routes (about, blog, careers, contact, FAQ, features, legal, pricing) from ever being shadowed; the redirect map is unit-tested.
- The landing is the only indexable app: it serves `robots.txt` (allow all) and a localized `sitemap.xml`. Copilot sends `X-Robots-Tag: noindex, nofollow` on every response, disallows `/` in `apps/copilot/app/robots.ts` and sets `robots: { index: false }` in its metadata; the control tower does the same.
- The assistant/MCP endpoint is at `apps/copilot/app/mcp/route.ts` (not under `/api`) and is excluded from the i18n middleware in `apps/copilot/proxy.ts`. Other API routes are under `apps/copilot/app/api/*`.
- ESLint is flat-config per workspace (`eslint.config.js`); the root `.eslintrc.js` only holds ignores. Prettier config is `.prettierrc` (with Tailwind class sorting); root `format` only covers `**/*.{ts,tsx}`.
